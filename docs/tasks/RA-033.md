# RA-033 — Kontekst zadania dla agenta: issue Jiry w transkrypcie case'a

## Goal

Gdy właściciel odpisze w wątku case'a utworzonego z issue Jiry, SUPERVISOR ma **widzieć samo
zadanie** (tytuł/status/opis issue), a nie tylko wiadomość właściciela. Dziś model dostaje z
RA-032 wyłącznie `case_messages` (wiadomość właściciela + poprzednie odpowiedzi agenta) — treść
issue reconciler rzutuje **tylko na Discorda**, nigdy do transkryptu. RA-033 domyka tę lukę.

## Kontekst decyzji (2026-08-24)

To jest **część 3** ciągu „agent czyta → myśli → działa". Właściciel wybrał wariant „read tools
first" (uziemione odpowiedzi), a śledztwo w kodzie wykazało, że pierwotnie zakładane warianty
katalogu narzędzi opierają się na infrastrukturze, której nie ma:

- **Filesystem read tools** (RA-012 `createImplementationToolset`) nie mają czego czytać: bare
  case Jiry nie ma bindingu repozytorium ani checkoutu; `LocalWorkspaceAdapter`/
  `createImplementationToolset` nie są konstruowane w żadnym procesie `apps/*` (tylko w testach).
- **Brokerowany read tool Jiry** (RA-021) to L: brak kompozycji brokera w workerze, brak żywego
  `ToolTransport` do Jiry (tylko fake'i — wzorzec CTF-018) i brak per-case grantu `project`
  (reconciler go nie tworzy → `resolveToolScope` odrzuciłby `OUT_OF_SCOPE`).
- **Realna, tania luka:** issue nie dociera do modelu w ogóle. Reconciler ma `summary`/`status`/
  `description` i rzutuje je tylko do outboxu `discord_case`; `readCaseMessages` czyta wyłącznie
  `case_messages`. To domyka Opcja 1.

Właściciel wybrał **Opcję 1** (statyczny kontekst wstrzyknięty przy reconcile), a nie Opcję 2
(aktywne narzędzie fetch). Aktywne narzędzia (broker + transport + grant) zostają na później.

## Kryteria akceptacji

- **AC1:** Reconciler zapisuje treść issue (klucz + status + summary + description) do
  `case_messages` w **tej samej transakcji** co korelacja, atomowo z utworzeniem case'a.
- **AC2:** Wpis jest oznaczony `role: SYSTEM`, `trust: UNTRUSTED_DATA` (issue to `UNTRUSTED_DATA` —
  `AGENTS.md` §5). Mutation check: zmiana markera na `TRUSTED` czerwieni test.
- **AC3:** Idempotencja — ponowny reconcile tego samego issue-snapshotu nie duplikuje wpisu
  (klucz `message_id = jira-issue:<eventId>`, `ON CONFLICT DO NOTHING`); zmiana issue (nowy
  `updated` → nowy `eventId`) dodaje świeży wpis odzwierciedlający nowy stan.
- **AC4:** Pola są przycięte tak, że body nie przekracza limitu `case_messages` (65_536) nawet przy
  wielkim opisie. Test jednostkowy renderera (bounds, puste pola, etykiety).
- **AC5:** Bramka zielona (Node 24), typecheck/build/lint/format, dwa przebiegi.

## Świadome zawężenia

- Bez aktywnych narzędzi (broker/transport/grant) — model **nie** pobiera issue na żądanie; dostaje
  je statycznie przy reconcile. To Opcja 2, przyszły task.
- Bez filesystem read tools (brak checkoutu dla bare case Jiry) i bez per-case workspace.
- `description` jest już parsowane przez `connector-jira` (RA-016); **nie** zmieniamy connectora ani
  pakietu `database` — cała zmiana żyje w `applyIssue` workera + mały czysty renderer.
- Okno kontekstu `listRecent` (domyślnie 20) może z czasem wypchnąć najstarszy wpis issue; przy
  aktywnym issue reconciler dokłada świeży kontekst przy każdej zmianie, więc pozostaje obecny.
