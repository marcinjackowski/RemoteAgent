# RA-022 — Policy, approvals and action executor

## Goal

Bezpiecznie wykonywać zewnętrzne write actions po deterministycznej policy i,
gdy wymagane, exact approval właściciela.

## Scope

- risk tier registry R0–R4 z Master Planu;
- deterministic policy engine poza modelem;
- canonical action payload i `action_digest`;
- propose -> policy -> Discord approve/reject/edit -> re-policy -> execute;
- approval owner/case/scope/digest/expiry binding i single consumption;
- osobny action executor bez model reasoning;
- idempotency/reconciliation/receipt dla provider writes;
- initial actions: Jira comment/status, Gmail draft, Calendar create/update/respond,
  GitLab comment/draft MR update;
- zawsze jawne R4: merge, force-push, delete, prod deploy, permissions;
- global/provider/connection/case kill switches;
- audit log bez sekretów i pełnych wrażliwych payloadów.

## Out of scope

Automatyczne production merge/deploy oraz admin/permission management.

## Acceptance criteria

1. Zmiana jednego parametru po approval unieważnia zgodę.
2. Approval jest jednorazowe, owner-scoped i odrzuca stale checkpoint revision.
3. Policy jest sprawdzana przy proposal i bezpośrednio przed execute.
4. Niepotwierdzony provider timeout daje `AMBIGUOUS` oraz reconciliation.
5. R4 nie może zostać auto-approved przez model ani remote tool annotation.
6. Kill switch działa również pomiędzy approval a execute.
7. Receipt wiąże action, provider result i external entity version.

## Required verification

- tampered payload/digest, replay, expired i wrong-owner approval tests;
- kill-switch race i policy-change race tests;
- provider timeout before/after side effect reconciliation tests;
- Discord proposal/buttons e2e z fake executor.

## Audit focus

Fail-closed semantics, TOCTOU między approval i execute, canonicalization, replay,
R4 invariants oraz brak autoryzacji opartej na deklaracji modelu.
