# RA-036 — Discord UX: informacja o błędzie agenta w wątku

**Status:** DONE  
**Zależy od:** RA-032 (DONE)  
**Milestone:** M7

## Kontekst

Gdy agent wpadnie w pętlę `AMBIGUOUS` i job trafi do DLQ (max attempts), wątek
Discord milczy — właściciel nie wie czy agent nad tym pracuje czy coś się
zepsuło. Brak widoczności błędów utrudnia diagnostykę i obniża zaufanie do
systemu.

## Cel

Gdy job `case.resume` zostanie dead-lettered (po wyczerpaniu `max_attempts`),
worker lub scheduler wyśle do wątku wiadomość z informacją o błędzie, np.:

> ⚠️ Agent encountered an error and could not complete this task. Please check
> the system logs or try again.

Wiadomość powinna być wyraźnie oznaczona jako błąd (emoji ⚠️ lub 🔴), nie
wyglądać jak odpowiedź agenta, i nie zawierać szczegółów technicznych (stack
trace) — tylko ogólny komunikat bezpieczny do wyświetlenia.

## Kryteria akceptacji

1. Gdy job `case.resume` wyczerpie `max_attempts` i przejdzie do DLQ, w wątku
   Discord pojawia się wiadomość błędu.
2. Wiadomość błędu nie zawiera stack trace ani wewnętrznych ID systemu.
3. Wiadomość błędu jest wyraźnie odróżnialna od normalnej odpowiedzi agenta
   (prefix ⚠️ lub analogiczny).
4. Mechanizm jest idempotentny — wielokrotne przejście do DLQ dla tego samego
   case'a nie tworzy wielu wiadomości błędów.
5. Jeśli case nie ma wątku Discord, błąd jest logowany ale nie crashuje procesu.
6. Istniejące testy nie regresują.

## Zrealizowany design (2026-08-25)

Nie osobny poller (rozważany w pierwotnym szkicu), lecz **lokalnie w handlerze**:
`JobStore.fail` dead-letteruje dokładnie gdy `lease.attempts >= max_attempts`, więc handler
`case.resume` wykrywa terminalny rzut tym samym porównaniem i tuż przed rzutem woła
`projectDeadLetterNotice`. Prostsze (bez nowego periodic taska), reużywa discord-owych zależności
workera, idempotentne producencko na `error:<jobId>` (bezpieczne na crash + re-claim). Gate
`reason === "owner_message"` — bo owner realnie czeka („agent nie odpowiedział"); recovery/
implementer passy nie zaśmiecają wątku.

Mapowanie AC:
- AC1 spełnione (terminalna próba = gwarantowany DLQ). AC2 — body to stała, user-safe stała bez ID/
  stack. AC3 — prefix ⚠️, oddzielne od odpowiedzi. AC4 — idempotencja na `jobId` (silniejsza niż per
  case). AC5 — brak bindingu → `false`, log, brak crashu. AC6 — całe repo 2457/2457 ×2.

## Scope (zrealizowany)

- `apps/agent-worker/src/dead-letter-notice.ts` (NOWY) — projekcja wiadomości błędu.
- `apps/agent-worker/src/handlers.ts` — wpięcie w terminalny rzut owner-driven `case.resume`.
- `apps/agent-worker/src/persistence.ts` — usunięcie tymczasowego diagnostyka `[markAmbiguous]`.

## Nie w scope

- Retry przez użytkownika z Discorda.
- Powiadamianie o dead-letterach spoza handler-throw (np. czysty reap lease bez ponownego claimu) —

- Szczegółowe logi błędów dla właściciela (detal został w `jobs.last_error`/DLQ dla operatora).
