# RA-034 — Agent DZIAŁA: IMPLEMENTER → realny lokalny commit

> **SUPERSEDED (2026-08-25) → M8 Engineering Control Plane (`ADR-0011`, RA-037..RA-044),
> z kwalifikacją iOS w RA-045.** Status `BLOCKED`. Write-loop budujemy jako jeden
> human-steered, durable workflow w istniejącym `SupervisorRuntime`, nie jako ad-hoc IMPLEMENTER
> ani drugi orchestrator. Zaczątki RA-034 (`implementer-work.ts`, `workspace-config.ts`) wchłaniają
> RA-041/RA-043/RA-045. Zob. `HANDOFF-01`
> (Decision Request) i `ADR-0011`.

## Goal

Doprowadzić do stanu, w którym uruchomiony IMPLEMENTER **faktycznie edytuje kod i robi lokalny
`git commit`** w izolowanym per-case workspace, pod writer fence. Bez push/MR (to osobny, późniejszy
task). To pierwszy realny „agent robi robotę", nie tylko rozmawia.

## Kontekst / stan wejściowy (śledztwo 2026-08-25)

Cztery niezależne braki w uruchomionym systemie (dowody w handoffie RA-033 i planie):

1. **Nikt nie tworzy IMPLEMENTERa.** Jedyna produkcyjna ścieżka tworzenia work unitu
   (`inbound-message.ts`) robi read-only SUPERVISORA; `agent.implementer` nie jest nigdzie
   enqueue'owany. `createImplementerHandler` (handlers.ts) czeka na job, którego nikt nie wysyła.
2. **Rola nie dostaje narzędzi.** `roles.ts:86` woła model bez `tools` — każda rola to czysty
   tekst→completion. `implementation-tools`/`workspace-runner`/`connector-gitlab` nie są importowane
   przez żaden plik `apps/*`.
3. **Brak provisioningu workspace.** `LocalWorkspaceAdapter` nigdzie w `apps/*` nie jest budowany;
   brak `workspaceRoot`, allowlisty repo, fence validatora, registry.
4. **Brak ścieżki MR.** Brak produkcyjnego `GitLabApi`/`BranchPusher` — poza testami. (Poza zakresem
   RA-034.)

Decyzja właściciela (2026-08-25): budujemy pierwszy realny write increment kończący się **lokalnym
commitem**; push/MR odłożone. Trigger IMPLEMENTERa na tym etapie jest **jawny** (metoda + payload
joba), nie autonomiczna decyzja SUPERVISORA (to zmiana kontraktu AgentCompletion — późniejszy task).

## Fakty z kodu istotne dla planu

- `RuntimeRoleInput = { unit, run, writerFence? }` (runtime.ts:83). IMPLEMENTER dostaje `writerFence`
  (`assertCurrent`/`release`), re-asERTowany przed i po wywołaniu modelu (runtime.ts:477,488).
- Work unit **nie** niesie `repositoryId`/`baseSha`/`branchName`; niesie `authoritative_scope`
  (`repo_allowlist`, `can_write_workspace:true`). Repo id → z `repo_allowlist`; baseSha/branch →
  z konfiguracji/derywacji (`git-lifecycle.branchNameFor` jest deterministyczne per case).
- `LocalWorkspaceAdapter.create` wymaga: `repositoryId` (klucz w `repositories` allowlist),
  `WorkspaceFenceValidator` (assertCurrent przed każdą operacją git), `WorkspaceRegistry`,
  `baseSha`, `branchName`, `identity {caseId, workspaceId}` (local-adapter.ts:80-105).
- Writer lease już istnieje: `WriterLeaseGuard` + `agent.implementer` job; worker buduje fence w
  `handlers.ts:90-107`. `WorkspaceFenceValidator` może opakować `fence.assertCurrent`.
- `createImplementationToolset` daje read+write+command; read filtruje ścieżki chronione
  (`.git`/`.env`/`AGENTS.md`…). Command ma server-owned katalog (model podaje tylko klucz).

## Kryteria akceptacji

- **AC1:** Produkcyjna ścieżka materializuje unit `role: IMPLEMENTER`, `can_write_workspace: true`,
  `repo_allowlist:[repoId]` i enqueue'uje `agent.implementer` — w jednej transakcji, idempotentnie,
  z guardem single-writer (jeden aktywny IMPLEMENTER per case, terminal case ignorowany). Test.
- **AC2:** Worker buduje `LocalWorkspaceAdapter` ze statycznej konfiguracji (`WORKSPACE_ROOT` + mapa
  repo allowlist z env) i provisionuje per-case worktree na starcie IMPLEMENTERa, pod fence
  (`WorkspaceFenceValidator` mostkuje writer lease). Test na throwaway repo git.
- **AC3:** Rola IMPLEMENTER dostaje toolset `implementation-tools` (write/patch/command + read)
  scope'owany do worktree, wpięty w `runStructuredCompletion` (`tools`+`execute`), **tylko** gdy
  trzymany jest fence. Read-only role bez zmian (nadal bez narzędzi). Test FakeTransportem
  emitującym tool-use.
- **AC4:** baseSha/branch policy: deterministyczny branch per case, base z konfigurowalnej gałęzi.
  Test.
- **AC5 (owner config):** Live smoke — właściciel podaje `WORKSPACE_ROOT` + repo (`repoId` + lokalny
  `sourcePath`), a realny model edytuje plik i robi lokalny commit na branchu case'a. Weryfikacja:
  commit istnieje na branchu w worktree, autor = proces, pod fence.
- **AC6:** Bramka zielona (Node 24), typecheck/build/lint/format, dwa przebiegi.

## Świadome zawężenia

- Bez push/MR (GitLab `GitLabApi`/`BranchPusher`/allowlist `writes_enabled`) — osobny task.
- Bez autonomicznego triggera SUPERVISOR→IMPLEMENTER (zmiana AgentCompletion) — trigger jawny.
- Bez review/test-evidence loop (RA-013/RA-015) w tej pętli — tylko edycja + commit.
- AC5 zależy od konfiguracji właściciela; części config-free (AC1-4, AC6) budowane i testowane
  niezależnie na throwaway repo.
