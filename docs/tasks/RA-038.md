# RA-038 — Trwałe operacje, eventy i recovery Engineering Control Plane

**Status:** DONE
**Zależy od:** RA-037  
**Milestone:** M8 — `ADR-0011`

## Cel

Rozszerzyć istniejącą persystencję runów/checkpointów o append-only operation
log, completion receipts i odtwarzalną projekcję etapów, bez równoległego
filesystem run-store.

## Zakres

- Migracje i repozytoria dla run/stage operations, model intents/completions,
  command receipts, plan/design revisions, slice attempts i loop events.
- Jednoznaczna tożsamość `case_id`, `run_id`, `op_id`, stage, attempt, owner i
  integration scope; FK, unique constraints i fencing token.
- Protokół intent→started→completion/receipt→projection/event.
- `prepareResume()` z klasyfikacją recovered, dirty, ambiguous, blocked i
  cancelled; operator-safe recovery bez ręcznej edycji DB.
- Lease renewal/expiry, deadline, cancellation i kill-switch observation.
- Minimalny operator port: read-only status oraz autoryzowane
  acknowledge/retry/cancel/reconcile z własnym intentem i receiptem.

## Kryteria akceptacji

1. Migracja ma działający down/rollback albo jawnie przetestowaną strategię
   forward-only zgodną z kontraktem repozytorium.
2. Write-once operation: byte/semantic-identyczny replay jest idempotentny, a
   ta sama tożsamość z inną treścią daje błąd integralności; mutation
   dopuszczająca overwrite daje RED.
3. Intent jest trwały przed model call, command lub side effectem. Brak pewnego
   receiptu po możliwym wykonaniu daje `AMBIGUOUS` i nigdy automatyczny replay.
4. Recovery po crashu: po intent, po completion, po command przed receipt i po
   receipt przed projection ma osobne testy na realnym PostgreSQL.
5. Stary/obcy fencing token, case/owner/integration mismatch i niezgodny digest
   są odrzucane fail-closed.
6. Projekcja bieżącego runu jest rekonstruowalna z niezmiennych operacji/eventów;
   test usuwa materializowaną projekcję i odtwarza równoważny stan.
7. Ownership map i migracja definiują: operation/event log jako historię
   przebiegu, `run_completions` jako write-once wynik runu, a `case_checkpoints`
   jako snapshot biznesowy/kontekstowy. Istniejący checkpoint revision, baseline
   i outbox zachowują semantykę.
8. Operator może odczytać stan i wykonać tylko policy-allowed acknowledge/retry/
   cancel/reconcile. Nie może wymusić `SUCCESS`, ominąć receipt/fence ani
   powtórzyć mutującej operacji o nieznanym wyniku.
9. Każda obserwowalna operacja niesie `run_id`, `case_id`, `op_id`, stage i
   attempt; cancellation/deadline kończy właściwym terminal reason.
10. `CTF-022` jest domknięty: `. scripts/dev/env.sh` wykrywa lub jawnie
   konfiguruje rzeczywiście dostępny lokalny PostgreSQL bez ukrytego skipu.
   Integracyjna bramka używa `RA_REQUIRE_POSTGRES=1`; exit code `0`.

Prompty, context selection, Bedrock, rzeczywiste gates i workspace writes.

## Ustalenia implementacyjne — 2026-08-26

- `job_intents`/`job_completions`/`job_reconciliations` pozostały jedynym
  ledgerem efektów. Nowe tabele przechowują wyłącznie engineering binding,
  strict artefakty, append-only stage/operator events i usuwalną projekcję.
- `STARTED` jest singletonem commitowanym bezpośrednio przed dispatch. Jego
  replay jest błędem wymagającym recovery, nigdy zgodą na drugi dispatch.
- Crash matrix jest fail-closed: bez `STARTED` i retry-safe bez completion są
  `DIRTY`; mutujący `STARTED` bez receiptu i `UNRESOLVED` są `AMBIGUOUS`;
  istniejący receipt/`CONFIRMED` są `RECOVERED`; `ABSENT` zezwala na nową
  operation identity; scope/fence/kill/deadline blokują.
- Operator nie nadaje outcome ani receiptu. Acknowledge/cancel/retry/reconcile
  są owner-scoped, strict, optimistic-digest i idempotentne. Reconcile zapisuje
  request przed efektem, deleguje tylko do `JobStore.reconcile()` i osobnym
  eventem obserwuje jego receipt; crash między nimi jest wznowialny.
- Globalna kolejność blokad control plane to `jobs→agent_runs→projection/event`.
  Audytowa mutacja odwrotnej kolejności deterministycznie kończy się
  `lock_timeout`; nie wolno reintrodukować `run→job` w nowych ścieżkach.
- Projekcja `engineering_run_projections` jest cache'em: delete + rebuild z
  ledgerów daje ten sam canonical digest. Nie jest źródłem autoryzacji ani
  historii.
- Pełna bramka wymaga aktualnego `dist` przed golden-path, bo suite failuje na
  stale build. Przed finalną komendą wykonano `turbo run build --force`, a sama
  komenda ponownie wykonała build bez cache.
