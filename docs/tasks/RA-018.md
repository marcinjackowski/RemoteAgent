# RA-018 — Golden path and concurrency proof

## Goal

Udowodnić kompletny Jira -> Discord -> Bedrock -> code -> tests/review -> GitLab
MR przepływ, w tym dwa równoległe taski i recovery po awarii.

## Scope

- spięcie komponentów M0–M3 bez pomijania publicznych kontraktów;
- dwa fixture/sandbox Jira issues w jednym lub dwóch allowlisted repos;
- dwa niezależne Discord threads, cases, workspaces i branche;
- co najmniej jedno trwałe pytanie decyzyjne i wznowienie po odpowiedzi;
- plan, implementacja, unit test, snapshot decision, review/fix i commit;
- push oraz dwa idempotentne draft MRs (fake lub jawny sandbox);
- pipeline feedback wracający do właściwego case;
- restart/fault matrix w każdej istotnej granicy;
- milestone runbook i zebrane artifacts/evidence.

## Out of scope

Gmail, Calendar, ogólne MCP write tools i produkcyjny deployment.

## Acceptance criteria

1. Dwa Jira taski rzeczywiście wykonują się równolegle bez współdzielenia zmian.
2. Ten sam case nigdy nie ma dwóch writerów.
3. Restart nie traci decyzji, planu, diffu, testów ani MR mappingu.
4. Crash przy niepotwierdzonym write kończy się reconciliation/AMBIGUOUS, nie replay.
5. Każdy MR wskazuje task, decyzje, testy, review i aktualny commit SHA.
6. `continue` po pytaniu wznawia właściwy case, nie inny thread.
7. Ponowne dostarczenie wszystkich eventów nie tworzy duplikatów.

## Required verification

- automatyczny e2e golden-path test;
- concurrency test dwóch cases z barierami potwierdzającymi overlap;
- process kill/fault injection matrix;
- manual Discord acceptance script;
- porównanie DB ledger, Git history, Discord i GitLab receipts.

## Audit focus

To jest pełna bramka milestone. Audyt musi sprawdzić system end-to-end, a nie
wyłącznie zielony test. Szczególny nacisk: izolacja, restart, idempotencja,
pytania decyzyjne i wiarygodność evidence.
